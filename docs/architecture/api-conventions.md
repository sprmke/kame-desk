# API conventions

Standing reference for `apps/api`'s REST surface. Read this before adding or changing an endpoint in any phase.

## Base

- All authenticated endpoints under `/api/v1`. Public (unauthenticated, clinic-facing) endpoints under `/api/v1/public/...` — kept in a visibly separate namespace so it's obvious at a glance which endpoints have no auth boundary and therefore need extra scoping discipline (see `docs/phases/phase-04-calendar-public-booking.md`).
- OpenAPI schema is auto-generated by FastAPI from routers + Pydantic schemas; `packages/api-client` is generated from that schema via Orval. Never hand-write a duplicate TS client.

## Request/response shape

- Request bodies and responses are Pydantic v2 schemas, named by intent: `PatientCreate` / `PatientRead` / `PatientUpdate` (never a single shared "Patient" schema for all three — read and write shapes diverge, e.g. computed fields like `age` or `bmi` only ever appear in `*Read`).
- List endpoints return a consistent envelope: `{ "items": [...], "total": int, "page": int, "page_size": int }` — not a bare array, so pagination metadata is never bolted on inconsistently per-endpoint later.
- Shared list query params: `page` (1-indexed), `page_size` (clamped to 25/50/100), optional `q`, optional `sort` as `field:asc` or `field:desc`. Helpers live in `app/core/pagination.py`.
- High-cardinality selectors use the same paginated endpoints. The web client debounces search, requests 25 rows, and fetches the next page near the end of the menu. Never fetch a fixed "large enough" roster for a dropdown.
- Appointments, invoices, claims, eligibility checks, LOA requests, and recalls omit `page_size` to return all matching rows (calendar, widgets, AI tools). Patients and the activity log always paginate.
- Errors: FastAPI's standard `HTTPException` with a JSON body `{ "detail": "..." }` for simple cases; for validation-style errors that the frontend needs to map to specific form fields, a structured `{ "detail": { "field": "message" } }` shape — document any endpoint that deviates from the default `{"detail": str}` shape in that endpoint's docstring.
- Never leak raw database/ORM errors (e.g. a raw Postgres exclusion-constraint violation message) to the client — catch known constraint violations and translate to a clean domain error (see Phase 3's double-booking 409 handling as the reference example).

## Auth & RBAC pattern

- Every protected route depends on `get_current_user` (resolves the JWT) and, where clinic-scoped, `require_clinic_role(*roles)` — a dependency factory that resolves the active clinic (from a path param or header) and checks the caller's `clinic_memberships` row for that clinic, re-checked on **every request**, never cached beyond the request lifecycle.
- Never trust a client-supplied `clinic_id` for scoping a query — always derive it from the resolved membership, even when the path also contains a `clinic_id` (validate the two match, don't just use the path value).
- Role checks are look up in the actual `mvp.md` §6.11 permission matrix per endpoint, not assumed from the general shape of the resource (e.g. billing is "Full" for reception per §6.11, but SOAP notes are "No access" by default for the same role on the same clinic).

## Public (unauthenticated) endpoint pattern

- Namespaced under `/api/v1/public/...`, always scoped by a clinic slug/token in the path, never by a raw numeric ID that could enumerate clinics.
- Rate-limited (IP-based is sufficient for MVP).
- Response payloads are hand-picked "safe" schemas (e.g. `PublicClinicRead`), never the same `*Read` schema used internally — an internal schema gaining a new field later must not silently leak it publicly. Introduced in Phase 4, reused by Phase 18's patient-facing assistant endpoints.

## Streaming (SSE) endpoints

- Used for: AI SOAP drafting (Phase 14), the AI Clinic Assistant's chat turns (Phase 16), the patient-facing assistant (Phase 18).
- Convention: `text/event-stream` response, each event a small JSON payload (`{"type": "token" | "field" | "tool_call" | "confirm_card" | "done" | "error", ...}`) — the frontend's SSE client dispatches on `type`, never parses free-form text.
- A dropped connection must leave the client in a clean, resumable-or-restartable state — no endpoint should require a perfect uninterrupted stream to produce a usable partial result.

## WebSocket endpoints

- `/ws/clinic/{clinic_id}` (Phase 5) — authenticated on connect, re-validated periodically (token expiry mid-session must force a reconnect, not silently keep a stale-auth socket open).
- Event payloads: `{"event": "appointment.visit_status_changed" | "appointment.created" | "notification.created" | "notification.updated" | ..., "data": {...}}`. Frontend reacts by invalidating the matching TanStack Query key, never by hand-patching client state from the payload. Notification events include `notification_id`, `type`, `title`, `body`, `href`, `actor_user_id` (no clinical PHI).
- Staff notification REST (Phase 40): `GET /api/v1/notifications`, `GET /api/v1/notifications/unread-count`, `POST /api/v1/notifications/{id}/read`, `POST /api/v1/notifications/read-all`, `GET/PATCH /api/v1/notifications/prefs`, `POST/DELETE /api/v1/notifications/push-subscriptions`. Scoped via `X-Clinic-Id` + membership; list filtered by role audience server-side.

## Reporting endpoints (Phase 12 pattern, reused by any later aggregate endpoint)

- Query params: `from_date`, `to_date` (ISO dates), optional `doctor_id`, optional `group_by`. Consistent across every `/api/v1/reports/*` endpoint.
- CSV export is a sibling route (`/api/v1/reports/{report}/export.csv`), same params, same RBAC as the JSON version — never a separate, more permissive export path.
- Clinic data export (Phase 21) uses `GET /api/v1/clinics/{id}/export/{patients|appointments}` and returns `text/csv`. Owner/admin only. Each download writes `clinic.data_exported`.

## Auth account endpoints (Phase 21)

| Method | Path                               | Notes                                                                          |
| ------ | ---------------------------------- | ------------------------------------------------------------------------------ |
| POST   | `/api/v1/auth/forgot-password`     | Always 204                                                                     |
| POST   | `/api/v1/auth/reset-password`      | Consumes hashed token, revokes all sessions                                    |
| POST   | `/api/v1/auth/verify-email`        | Consumes hashed token                                                          |
| POST   | `/api/v1/auth/resend-verification` | Authenticated                                                                  |
| GET    | `/api/v1/auth/sessions`            | Active refresh sessions                                                        |
| POST   | `/api/v1/auth/logout-everywhere`   | Revoke all refresh rows                                                        |
| GET    | `/api/v1/auth/me`                  | User + memberships; with `X-Clinic-Id`, also `active_clinic` + `permissions[]` |

`GET /auth/me` without `X-Clinic-Id` returns identity and all memberships only. With `X-Clinic-Id`, the response adds the active clinic `{ id, name, role }` and a sorted `permissions` list computed in `app/core/permissions.py` from role + clinic flags (e.g. `reception_can_view_soap`). The web app uses this for sidebar and settings nav filtering; API routes still enforce RBAC independently. Missing or inactive membership returns `403` with `{ "code": "NO_ACTIVE_MEMBERSHIP", "message": "..." }`.

Password-reset and email-verify tokens live in `account_tokens` (SHA-256 hash, never stored raw).

| Method   | Path                              | Notes                                                                        |
| -------- | --------------------------------- | ---------------------------------------------------------------------------- |
| GET/POST | `/api/v1/eligibility-checks`      | List: `q`, `status`, `payer_type`, `patient_id`, `page`, `page_size`, `sort` |
| PATCH    | `/api/v1/eligibility-checks/{id}` | Status, verified amount, notes                                               |

## Versioning

- `/api/v1` is the only version for the MVP's lifetime. If a breaking change is ever needed, it gets a new `/api/v2` prefix and both are served during a migration window — do not silently break `/api/v1` clients (including the AI assistant's own tool calls, which are just internal HTTP calls against this same surface).

## Idempotency

- Any endpoint a Tier 1 AI tool (Phase 16) might call automatically must be idempotent — calling it twice with the same input produces the same end state, not a duplicate side effect. Design new mutating endpoints with this in mind even before Phase 16, since retrofitting idempotency later is harder than building it in from the start.
