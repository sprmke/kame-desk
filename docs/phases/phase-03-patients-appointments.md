# Phase 3: Patients + appointments + exclusion constraint

**Status:** Done
**Depends on:** Phase 2
**Unlocks:** Phase 4

**mvp.md reference:** §6.3, §6.4 (data model + core CRUD only — calendar UI is Phase 4), §7.5 (global patient search) · Gap closed: #5 in §7

## Goal

Patients exist as real records with full demographic/medical data and file attachments, and appointments can be created against them with the **hard database-level guarantee that double-booking is impossible**, even under concurrent requests. This phase is data model + API + basic list/detail UI; drag-and-drop calendar UX is Phase 4.

## Prerequisites

- Phase 2 done: doctors exist with working hours, so appointment validation has something to check against

## Tasks

### 1. Database

- [ ] `patients` table — clinic_id, patient_number (auto-generated, sequential per clinic), full_name, birthdate, sex, civil_status, occupation, contact_number, email, address, emergency_contact (jsonb: name/relationship/number), insurance_info (jsonb: provider/member_id/coverage_notes), created_at/updated_at, created_by_user_id
- [ ] `patient_medical_info` table (or columns on `patients` — decide based on query patterns, document the decision) — allergies (structured: array of `{substance, reaction, severity}`, **not free text**, per mvp.md §6.3 "required for AI drug-interaction checks"), medical_history, family_history, surgical_history, current_medications (structured array), chronic_conditions, vaccination_history
- [ ] `patient_vitals` table — patient_id, recorded_at, height_cm, weight_kg, bmi (computed), blood_pressure, temperature_c, heart_rate, respiratory_rate, spo2, recorded_by_user_id, visit_id (nullable — vitals can be recorded standalone or per-visit, see Phase 7)
- [ ] `patient_files` table — patient_id, r2_key, file_type (`lab_result`/`xray`/`ultrasound`/`mri_ct`/`image`/`pdf`/`other`), uploaded_at, uploaded_by_user_id, visit_id (nullable), description
- [ ] `rooms` table (optional per clinic — only needed if a clinic has more than one consult room, per mvp.md §6.4) — clinic_id, name
- [ ] `appointments` table — clinic_id, patient_id, doctor_id, room_id (nullable), scheduled_start, scheduled_end, reason_for_visit, notes, appointment_status (`Scheduled`/`Confirmed`/`Cancelled`/`No Show`/`Rescheduled`), created_by_user_id, created_at/updated_at
- [ ] **Exclusion constraint** (the hard guarantee): `btree_gist` extension (enabled in Phase 1) + `EXCLUDE USING gist (doctor_id WITH =, tsrange(scheduled_start, scheduled_end) WITH &&) WHERE (appointment_status NOT IN ('Cancelled', 'No Show', 'Rescheduled'))` — per doctor. Add a second exclusion constraint on `room_id` when a room is assigned, same shape.
- [ ] Alembic migration for the exclusion constraints must be hand-reviewed, not blindly autogenerated — Alembic's autogenerate does not reliably detect `EXCLUDE` constraints; write the `op.execute(...)` DDL explicitly and add a matching `downgrade()`.

### 2. Backend

- [ ] `GET /api/v1/patients` — paginated, filterable, **fuzzy search** on name/contact/patient_number (Postgres `pg_trgm` or `similarity()`; document the choice in `docs/architecture/data-model.md`)
- [ ] `POST /api/v1/patients`, `GET/PATCH /api/v1/patients/{id}` — full CRUD except delete (patients are never hard-deleted; add an `is_archived` flag if a clinic needs to "remove" one)
- [ ] `PUT /api/v1/patients/{id}/medical-info` — allergies/history/medications, structured input validated by Pydantic (allergy list is a typed model, not `str`)
- [ ] `POST /api/v1/patients/{id}/vitals` — record a vitals entry
- [ ] `POST /api/v1/patients/{id}/files` — presigned R2 upload URL issuance + file metadata row creation
- [ ] `GET /api/v1/patients/{id}/files` — list, filtered by type/visit
- [ ] `POST /api/v1/appointments` — validates: doctor belongs to clinic, slot within doctor's working hours (from Phase 2), no conflicting exclusion-constraint violation (catch the DB exception and return a clean 409 with the conflicting appointment, don't leak a raw Postgres error)
- [ ] `GET /api/v1/appointments` — filterable by doctor/date range/status/patient
- [ ] `PATCH /api/v1/appointments/{id}` — reschedule/status change (full drag-and-drop UX lands Phase 4, but the endpoint and validation exist now)
- [ ] All endpoints scoped by `require_clinic_role` and clinic membership; reception/doctor/admin/owner per the §6.11 matrix (patients + scheduling = "Full" for all four roles)

## Edge cases & safety

- **Concurrency**: two front-desk tablets booking the same doctor/slot simultaneously — the exclusion constraint must reject the second write at the DB level; write a load test (e.g. `pytest` + `asyncio.gather` of concurrent inserts) that proves this, not just a manual check (mvp.md §12: "load-tested, not just single-user tested").
- Allergy data structure must support "none known" as a distinct, explicit state from "not yet asked" (empty list is ambiguous — use a `allergies_reviewed: bool` flag or similar).
- Patient files: presigned URLs must be short-lived (e.g. 15 minutes) and never cached client-side beyond the session.
- Fuzzy search must be clinic-scoped — never return another clinic's patient in results, even a partial match.
- Appointment validation against working hours must account for the clinic's timezone (`Asia/Manila` default) correctly across DST-free PH time — store timestamps in UTC, convert at the edge.
